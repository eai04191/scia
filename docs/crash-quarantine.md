# クラッシュした投稿の隔離

特定の投稿を描くとアプリが落ちると、起動するたびに既読位置のその投稿で落ちて、使えなくなる。次の起動でその投稿だけを隠し、使う人が選んだときだけ開発者に手がかりを送る。

## 記録

- 投稿の行を組み立てる直前、高さを測る直前、レイアウトの直前に、その投稿のIDを記録する（`CrashMark`）。投稿がブーストなら元の投稿のID、通知なら対象の投稿のIDにする
- 記録はMAP_SHAREDで対応づけたファイルに書く。行ごとに書くので、ファイルの書き込みにしない
- シグナルハンドラーは、メインスレッドのクラッシュで、処理中のIDがあるときだけ「クラッシュした」と書く。ほかのスレッドのクラッシュは、処理中の行のせいとは言えないので書かない
- ハンドラーは元の扱いに戻して投げ直す。OSのクラッシュログ（TestFlightに届くもの）を今までどおり残すため
- Machの例外ポートは差し替えない。シグナルで足りることをテストで確かめた（abort、不正なメモリアクセス、トラップ、スタックオーバーフロー）
- メインのRunLoopが待ちに入る前（CATransactionのコミットのあと）に処理中のIDを消す。処理を終えた行の記録が残ると、あとで起きた関係のないクラッシュをその行のせいにするため

## 隔離の条件

- ハンドラーが動いたときだけ隔離する。メモリ不足、ウォッチドッグ、使う人の強制終了ではハンドラーが動かないので、隔離もチップも出ない
- 1回目のクラッシュから隔離する。どのアカウントの投稿かは、チップをどのアカウントで出すかに使う。隠すかはアカウントを問わずに引く。複数のウィンドウで別のアカウントを開けるため
- ビルドが変わったら解除する。直ったあとも隠したままにしないため。クラッシュのあと起動する前に更新されたときの記録も、前のビルドのものなので隔離に使わない

## 隠し方

- ストアは変えず、タイムラインの行の中身だけを読めない行に差し替える（`TimelineViewController.quarantined`）。IDは元のままなので、既読位置、未読の数、スクロールの基準は影響を受けない
- 隠した投稿の行は押すと送る内容の画面を開く。投稿の中身は、その画面の「ブラウザで開く」で確かめられる。ブラウザはSciaの描画を通らないため、開いても落ちない

## 伝え方

- 起動後に一度だけ、タイムラインの上にチップを出す。押すと送る内容の画面を開く。起動直後に割り込む画面は出さない
- 同じ投稿では二度伝えない。投稿が原因とは限らないので、文言は断定しない

## 送る内容

- 投稿の変換や本文の解析が原因かもしれないので、APIの応答をモデルに変換せず、JSONのまま読む。画面で投稿の行の部品を使わない
- 公開と未収載の投稿はURLだけを送る。公開範囲が分からない投稿は誰でも読めるとは扱わない
- フォロワー限定とダイレクトの投稿は、本文を含まない構造の要約を、人が読める文章で送る。書いた人の本文を開発者に渡さないため
- 文字を置き換えたJSONは、使う人がオンにしたときだけ、全文を見せて足す。文字数の上限があるので、メールでのみ送れる
- 要約も置き換えたJSONも、出す項目をコードで作る。JSONから丸ごと写さない。サーバーが独自の項目を足しても、中身が混ざらないようにするため
- 画面に出した文字をそのまま送る。アプリの版と機種も、その文字に含める

## 画面の説明

- 行やチップから来た人は何が起きたかを知らないので、最初に、問題が発生したため表示を中止したことを謝り、原因を直すために情報の提供を頼む。投稿が原因だと断定しない
- そのあとに、投稿を見る手段、報告する内容の順に置く。要約では、該当しない項目は出さない
- 報告の内容を読み込めないときも、タイムラインが持っていた投稿のページをブラウザで開けるようにする

## 送り先

- メールか、Mastodonのダイレクト。メールは`mailto:`で、使う人が既定にしたメールアプリで開く。どちらも送信は使う人が押す。宛先は`Config/app-info.json`の`contact`
- Mastodonのダイレクトは投稿欄を開いて本文を入れる。書きかけがあれば上書きせず、開かない
- GitHubのissueは公開なので使わない
- PRIVACY.mdには書かない。アプリは内容を投稿欄かメールアプリに入れるだけで、自動的には送らないため
