# Vision

## なぜ作るか

Sciaは、Mastodon歴8年・34万投稿の作者が、自分のメインクライアントとして使うために作るiOSアプリである。

作者はこれまでMonaを使ってきた。手触りは良いが、不満もあった。いちばん大きいのはストリーミングAPIに対応する予定がないことで、ほかにもトランジションが部分的に壊れていることや、タイムラインを更新するだけでもAPIリクエストが多く、通信が遅いことがある。Sciaは、Monaのような手触りを土台に、これらの不満を解消し、作者の使い方に合わせた機能を足していく。

## 目指すもの

- ストリーミングAPIで新着が流れてくる。読んでいる最中に新着が来ても視点が動かない
- 流れの速いタイムラインでも、まとめて挿入する、最上部にいるときだけ自動で流すなどの制御によって、目で追えて重くならない
- バックグラウンドからの復帰や再接続のときも、取りこぼしや重複なくタイムラインがつながる
- トランジションが壊れない。アニメーションの途中でも操作を受け付け、どこで止めても破綻しない
- 通信が速い。必要なリクエストだけを送り、更新のたびに待たされない
- 通知タブを開かなくても、自分への反応（お気に入り、ブースト、返信、フォローなど）に気づける。読んでいる画面を邪魔しない場所に出す
- 作者が毎日メインのクライアントとして使える。一般向けのクライアントが載せないような細かい機能（説明にならない代替テキストを隠す、一覧でも元の画質で表示するなど）でも、作者が毎日使うなら載せる

## 判断の基準

- いまの対象は作者1人。万人向けの分かりやすさより、作者の手に馴染むことを優先する
- 納得のいくものができれば、TestFlightやApp Storeでの公開も視野に入れる。そのため、作者の好みに寄せた挙動も、ハードコードせず設定で切り替えられる形にしておく
- 機能の数より、毎日触る操作の質を優先する

## 想定外の応答への向き合い方

Sciaは、作者が試していないサーバーの実装や版、手前のプロキシとも話す。APIが仕様どおりに返さないことを前提にする。

- クラッシュと、一時的なエラーによるログアウトは、いちばん避ける。資格情報を消すのは、使う人がログアウトを選んだときだけにする
- 読めた分は読めるようにする。一部が読めなくても全体を失敗にせず、読めなかったことは隠さずに示す
- 失敗しても、表示している内容は消さない
- 自動の読み込みの失敗は、アラートにしない。表示している内容に関わる失敗は一覧の中やバーで知らせ、使う人にできることがない失敗はログだけにする
- 失敗は種類ごとの文言で知らせ、HTMLの本文や英語のデコードの説明のような、使う人に意味のない文は出さない
- 自動で送り直すのは、送り直しても結果が変わらないリクエストだけにする
- 失敗の原因は、リリース版の記録だけで絞れるようにする

## アプリ内通知

操作の結果や失敗を知らせるときの考え方。どの場面でどう出すかは[notices.md](notices.md)にある。

- アプリ内通知の重さを、知らせる内容の重さに合わせる。操作を止めるアラートは、そのままでは書いたものが失われるか誤解を生む失敗と、設定を変えないと直らない失敗だけにする。押し直せば済む失敗は、操作を止めずに知らせる
- 成功は、画面の変化で見えないときだけ知らせる。うまくいくのが当たり前なので、知りたいのは失敗したときだけ
- 画面の中の対象に結び付いた状態は、その対象の近くに出す
- 画面の中の対象に結び付かないアプリ内通知は、画面ではなくアプリに属する。画面を移っても一緒に流さず、どの画面を開いていても見えるようにする
- 押せるアプリ内通知は、押せることが見て分かるようにし、押そうとしている間に位置を動かさない
- 消えたアプリ内通知の失敗も、あとから確かめられるようにする

## 一覧の動き

一覧の行が増えたり消えたり、高さが変わったりするときに、動かすかどうかの考え方。HIGのMotionにある、動きは目的のあるときだけ足し、操作の結果を短く正確に伝えるという考えに沿う。読んでいる最中に視点を動かさないことを、動きで伝えることより優先する。

- 使う人がその行に対して行った操作の結果で行が消えるとき（フォローリクエストの承認・却下、投稿の削除など）は、UIKit標準の削除の動きで、行を閉じて下の行を詰める。押したものが片づいたことを、目で追える形で伝えるため
- 使う人の操作によらない変化（ストリーミングの新着や削除、ギャップや古い投稿の読み込み、フィルター、再接続の補完）では動かさず、読んでいる行の位置を保つ。最上部で新着に追従するときだけは、設定で動きを選べる
- 操作の結果でも、表示領域の上端より上の行が消えるときと、行の追加や中身の変化、操作によらない削除と一緒に起きるときは動かさない。詰めたり高さが変わったりして読んでいる行がずれるのと、操作によらない変化まで動いて見えるのを避けるため
- 見えている行の高さが変わるとき（リンクのカードが届くなど）は、下の行ごと動かしてつなぐ。上端が表示領域より上にある行は、動かさずに位置を保つ
- 視差効果を減らす設定では動かさない
- 動きの途中でも、スクロールや次の操作を受け付ける

## 投稿欄

- 投稿は、タブバーの上のインライン投稿欄だけで書く。全画面の投稿画面は持たない。全画面ではタイムラインが見えないので、部品を足して欄が大きくなっても失うものはない
- 画面の小さい機種で一覧を広く使えるよう、設定で、書いていないときの空の投稿欄を隠せるようにする。書くときは一覧の右上のボタンで出す。下書きや返信先が残っているときは、残っていることに気づけるよう隠さない。右上のボタンは、欄が見えているかにかかわらず出したままにし、押そうとしている間に位置を変えない。隠すときは、薄くして消さず、キーボードが去る方へ一緒に下げて、タブバーの裏から画面の外へ出す。欄はキーボードに乗って動いているので、別の消え方をすると、閉じる操作の中で欄だけが別の動きをして見えるため。出すときは逆に、下からキーボードと一緒に上げる
- 書いていないときのカプセルにも、返信や編集をしていることと、添付があることを、文字を増やさずにアイコンとサムネイルで出す。カプセルにしても下書きの中身を見失わないようにするため。開閉では同じものを同じものの位置へ動かし、カプセルと書いているときの欄が同じものだと分かるようにする。決まりは[compose.md](compose.md)の「書いていないときの1行」にある
- 添付、注意書き、投票などの部品を足すボタンは、＋ボタンの中にまとめる。書いていないときや短い投稿のときに、欄を大きくしない。よく使うものは、使う人が設定でボタンの行に常に出せる。決まりは[compose.md](compose.md)の「＋のメニューとボタンの行」にある
- 閲覧注意は、Mastodonのweb UIと同じく、注意書きの欄で兼ねる。添付のある投稿で注意書きの欄を出していれば、添付を閲覧注意にし、欄が空なら注意書きなしで閲覧注意だけを付ける。サーバーは注意書きのある投稿を必ず閲覧注意にするので、別の項目にすると、注意書きがある間は付いたまま押せない項目になる。兼ねれば、＋の項目も増えない。空の欄で閲覧注意になることは、欄の案内と、サムネイルの右上の目の印で見せる
- アカウントの「既定で閲覧注意にする」は、web UIと同じく、最初の添付を足したときに注意書きの欄を開いて反映する。開いた欄で、閲覧注意が付いたと分かるようにするため
- 本文は決まった行数までは伸ばし、超えたら欄の中でスクロールする。書いている途中に欄が広がって、見ているタイムラインを隠さないようにするため
- 長い投稿や部品の多い投稿のために、展開ボタンで本文の行数の上限を外せるようにする。広げた状態が、全画面の投稿画面の代わりになる。押してもすぐ上端までは広げず、本文に合わせて伸ばし、安全領域の上端に届いたら欄の中でスクロールする。いきなり上端まで広げると、短い投稿では空白ばかりになり、見ているタイムラインを必要以上に隠すため。本文が上限の行数より短ければ、上限の行数の高さまで広げ、書き足す行の場所を先に取る
- メンション、ハッシュタグ、カスタム絵文字の補完の候補は、欄の上にタイムラインへ重ねて縦に並べる。候補の行を欄の中に足すと、打つたびに欄の上端が動くため。広げていても、欄の上に場所が残っていれば欄の上に出す。上端まで伸びて欄の上に場所がないときだけ、打っている行のすぐ下に重ね、入りきらなければ行の上に重ねる
- 補完の候補は、いちばん優先するものを打っている文字にいちばん近い端に置く。入力の上に出すときは一番下から積み、行の下に出すときは一番上から並べる。UIKitのメニューの`priority`の並び順と同じ考え方で、指と目の動きが短くなり、あとから候補が足されても押そうとしている候補が動かない。ハードウェアキーボードの↑↓は見た目の向きに動かし、VoiceOverは見た目にかかわらず、いちばん優先する候補から読み上げる
- カスタム絵文字は、一覧を手元に持っていて問い合わせないので、`:`のあと1文字から候補を出す。0文字（`:`だけ）にすると、「例:」のように日本語の直後の`:`のたびに出るため
- 日本語の直後に打った`@`・`#`・`:`でも候補を出し、選んだら前に空白を入れる。サーバーは日本語の直後をメンション、タグ、絵文字として読まないが、日本語の文の途中で空白を意識せずに使えるようにするため。英数字や`/`の直後は、メールアドレス、URL、時刻の一部とみなして出さない
- ハッシュタグの補完では、プロフィールに載せているタグと最近使ったタグ（`featured_tags`と`featured_tags/suggestions`）を、サーバーの検索結果より上に出す。サーバーの検索は自分が使ったかを見ず、名前の短い順やサーバー全体の人気で並べるため、よく使うタグが押し出されるため。打った語で始まるものを先に、語を含むものを後に並べ、それぞれの中ではプロフィールのタグを先にする。端末に使ったタグを記録することはしない
- 注意書きの欄では、カスタム絵文字だけを補完する。サーバーは注意書きの絵文字は描くが、メンションとタグは処理しないため
- 自分の投稿の編集も、投稿欄で行う。返信先の札の行を編集の札に使い、行を増やさない。編集では返信先を変えられないので、返信の編集なら返信先も編集の札に書く。札の×で編集をやめる
- 編集では公開範囲を変えられないので、公開範囲は今の範囲を見せたまま選べなくする
- 編集を始めるとき、書きかけの下書きがあれば、捨ててよいか聞く。下書きを脇によけて編集のあとに戻すことはしない。下書きを残す仕組みは、アプリを起動し直しても残る下書きとして作る
- 投票の付いた投稿の編集では、投票を元のまま送り直す。サーバーは送らなかった投票を消すため。締め切りは送った時点から数え直されて少しずれるので、編集を始める前に知らせる。締め切りまで5分を切った投稿は、サーバーが受け付けないので編集できなくする
- ハードウェアキーボードでの候補の選び方は、Mastodonのweb UIと同じにする（Tab・Returnで確定、↑↓で選ぶ候補を移す、Escで閉じる）。Returnを奪うのは候補を出している間だけで、変換中は候補を出さないので、変換の確定とはぶつからない

## サーバーのフィルター

- 自分の投稿には、フィルターを当てない。公式のWebクライアントと同じ。サーバーは自分の投稿にも一致したフィルターを付けるが、当てると、投稿した直後の自分の投稿が隠れて、投稿に失敗したように見えるため
- 代わりに、自分の投稿がフィルターに一致したら、畳まずに「フィルター「A」に一致」の1行を出す。昔作ったフィルターに一致する話題を自分が書くと、それに触れた人の投稿が黙って隠れ、フィルターがあることに気づけないため
- フィルターが変わったこと（ストリーミングの`filters_changed`）が届いても、表示している投稿には反映しない。読み込み直したときに反映される。表示している投稿に反映するには、一覧を読み込み直すか、キーワードを手元で照らし合わせる必要があり、作業が大きいため

## 当面やらないこと

- Monaの全機能の再現。作者が毎日使う機能に絞る
- リスト、ローカル、連合タイムライン
- プッシュ通知
- macOS対応。iOSで手触りが固まってから、SciaCoreを共有する形で着手する
- Mastodon以外（Misskeyなど）への対応
