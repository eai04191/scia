# Vision

## なぜ作るか

Sciaは、Mastodon歴8年・34万投稿の作者が、自分のメインクライアントとして使うために作るiOSアプリである。

作者はこれまでMonaを使ってきた。手触りは良いが、不満もあった。いちばん大きいのはストリーミングAPIに対応する予定がないことで、ほかにもトランジションが部分的に壊れていることや、タイムラインを更新するだけでもAPIリクエストが多く、通信が遅いことがある。Sciaは、Monaのような手触りを土台に、これらの不満を解消し、作者の使い方に合わせた機能を足していく。

## 目指すもの

- ストリーミングAPIで新着が流れてくる。読んでいる最中に新着が来ても視点が動かない
- 流れの速いタイムラインでも、まとめて挿入する、最上部にいるときだけ自動で流すなどの制御によって、目で追えて重くならない
- バックグラウンドからの復帰や再接続のときも、取りこぼしや重複なくタイムラインがつながる
- トランジションが壊れない。アニメーションの途中でも操作を受け付け、どこで止めても破綻しない
- 通信が速い。必要なリクエストだけを送り、更新のたびに待たされない
- 作者が毎日メインのクライアントとして使える。一般向けのクライアントが載せないような細かい機能（説明にならない代替テキストを隠す、一覧でも元の画質で表示するなど）でも、作者が毎日使うなら載せる

## 判断の基準

- いまの対象は作者1人。万人向けの分かりやすさより、作者の手に馴染むことを優先する
- 納得のいくものができれば、TestFlightやApp Storeでの公開も視野に入れる。そのため、作者の好みに寄せた挙動も、ハードコードせず設定で切り替えられる形にしておく
- 機能の数より、毎日触る操作の質を優先する

## 想定外の応答への向き合い方

Sciaは、作者が試していないサーバーの実装や版、手前のプロキシとも話す。APIが仕様どおりに返さないことを前提にする。

- クラッシュと、一時的なエラーによるログアウトは、いちばん避ける。資格情報を消すのは、使う人がログアウトを選んだときだけにする
- 読めた分は読めるようにする。一部が読めなくても全体を失敗にせず、読めなかったことは隠さずに示す
- 失敗しても、表示している内容は消さない
- 自動の読み込みの失敗は、アラートにしない。表示している内容に関わる失敗は一覧の中やバーで知らせ、使う人にできることがない失敗はログだけにする
- 失敗は種類ごとの文言で知らせ、HTMLの本文や英語のデコードの説明のような、使う人に意味のない文は出さない
- 自動で送り直すのは、送り直しても結果が変わらないリクエストだけにする
- 失敗の原因は、リリース版の記録だけで絞れるようにする

## 知らせ方

操作の結果や失敗を知らせるときの考え方。どの場面でどう出すかは[notices.md](notices.md)にある。

- 知らせの重さを、知らせる内容の重さに合わせる。操作を止めるアラートは、そのままでは書いたものが失われるか誤解を生む失敗と、設定を変えないと直らない失敗だけにする。押し直せば済む失敗は、操作を止めずに知らせる
- 成功は、画面の変化で見えないときだけ知らせる。うまくいくのが当たり前なので、知りたいのは失敗したときだけ
- 画面の中の対象に結び付いた状態は、その対象の近くに出す
- 押せる知らせは、押せることが見て分かるようにし、押そうとしている間に位置を動かさない
- 消えた知らせの失敗も、あとから確かめられるようにする

## 投稿欄

- 投稿は、タブバーの上のインライン投稿欄だけで書く。全画面の投稿画面は持たない。全画面ではタイムラインが見えないので、部品を足して欄が大きくなっても失うものはない
- 添付、注意書き、投票などの部品を足すボタンは、＋ボタンの中にまとめる。書いていないときや短い投稿のときに、欄を大きくしない
- 本文は決まった行数までは伸ばし、超えたら欄の中でスクロールする。書いている途中に欄が広がって、見ているタイムラインを隠さないようにするため
- 長い投稿や部品の多い投稿のために、展開ボタンで欄を安全領域の上端まで広げられるようにする。広げた状態が、全画面の投稿画面の代わりになる。本文の長さに合わせて伸ばさず、押したらすぐ上端まで広げる。打つたびに欄の上端が動かないようにするため

## 当面やらないこと

- Monaの全機能の再現。作者が毎日使う機能に絞る
- リスト、ローカル、連合タイムライン
- プッシュ通知
- macOS対応。iOSで手触りが固まってから、SciaCoreを共有する形で着手する
- Mastodon以外（Misskeyなど）への対応
