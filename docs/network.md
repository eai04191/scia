# 通信

アプリの通信（REST API、ログイン、ストリーミング、画像、動画の先頭、共有と保存のダウンロード、リンク先のページ、Xの投稿）を送るときに、作者が決めたこと。決まりを経路ごとに作ると、目の前の経路にしか効かないため、すべての経路を1つの入口に通して、そこで守らせる。

## 入口

- 通信はすべて`HTTPClient`を通す。ストリーミングの接続は`StreamingClient`が、同じ門と同じ分け方で開く
- URLSessionを使うのは`URLSessionTransport`だけにする。ほかの場所でURLSessionを直接使う書き方は、`make lint`の`url_session_outside_network_layer`で止める
- httpとhttps（WebSocketはwsとwssも）以外のURLは送らない。URLSessionは`file:`や`data:`も読めるため、サーバーが返したURLで端末のファイルを読みに行かないようにする。デバッグのダミー投稿の`data:`のURLは、デバッグ用の障害の差し込み（`FaultInjectingTransport`）が返す
- 動画の再生（`AVPlayerItem(url:)`）だけは、この入口に通さない。AVFoundationが、範囲を区切って読む長さや先読みの量を自分で決めて読むため。通すには、独自のスキームで受けて中身をすべてこちらで返す仕組み（`AVAssetResourceLoader`）が要り、シークや先読みを作り直すことになる。再生は使う人が開いたときだけの通信なので、外れるのは自動の通信を止める決まりだけで済む

## 通信の目的

どの経路も、通信を、使う人がそれを待っているかで4つに分け（`RequestPurpose`）、レート制限で止めるかと、回線で控えるかを、この分け方だけで決める。経路ごとにモバイル通信かを読み分けると、控える経路と控えない経路が混ざり、新しく足した経路が決まりから漏れるため。

| 目的 | 例 | 止められている間 | 低データモード | モバイル通信 |
|---|---|---|---|---|
| 操作（`action`） | 投稿、ビューアを開く、投稿のメニューを開く、共有と保存、リンクのタイトル、ログイン、引っぱって読み込み直す | 送る | 送る | 送る |
| 表示（`display`） | つなぎ直し、ポーリング、切れていた間の補完、既読位置の保存、投稿欄の補完、行に描くアイコン・絵文字・サーバーのプレビュー画像、リンクのカード、Xの投稿 | 送らない | 送る | 送る |
| 質を上げる（`enhancement`） | 一覧のサムネイルの元の画像、動画の最初のコマ | 送らない | 送らない | 設定がオンのときだけ送る |
| 先読み（`prefetch`） | まだ画面に出ていないものを、開いたときに待たせないために読む | 送らない | 送らない | 送らない |

- 表示は、それがないと行が描けないか、一覧が古いままになる通信。質を上げるは、同じ場所に安い代わり（サーバーのプレビュー画像）があり、送らなくても表示が欠けない通信
- 新着を挿入する前に読むアイコンは、すぐに描くので、先読みではなく表示に入れる
- 動画の再生は、使う人が開いたときだけの通信なので操作に入れる。入口に通さない理由は上にある
- 設定は「モバイル通信で高画質のサムネイルを使う」の1つにし、質を上げる通信をまとめて切り替える。低データモードでは、設定によらず送らない。端末の設定で使う人が通信量を減らすよう求めているため
- 送ってよいかを回線と設定から決めるのは、`NetworkUsePolicy`だけにする。呼び出し側は、目的を名乗って送ってよいかを聞き、読むもの（プレビューか元の画像か）を選ぶ。回線の状態を直接読んで分ける書き方は、`make lint`の`network_conditions_outside_policy`で止める
- 質を上げると先読みのリクエストには、同じ決まりで`URLRequest`の`allowsConstrainedNetworkAccess`と`allowsExpensiveNetworkAccess`を付ける。呼び出し側が聞いたあとでWi-Fiからモバイル通信に変わっても、OSが送らない。OSが送らなかったら、回線で控えた失敗にする（下の「失敗の分け方」）

## 失敗の分け方

どの経路も、失敗を次の4つに分け（`HTTPFailure`）、送り直すか、待って読み直すか、あきらめるかを、この分け方だけで決める。経路ごとにステータスを読み分けると、429を「読めない」として二度と読まない経路が出るため。

- 待てば直る: 通信の失敗、408、429、5xx、自動の通信を止めている間。応答が再開の時刻を示していれば、その時刻も持つ
- 認証の失敗: 401。トークンが無効かは、セッションが確かめる。ストリーミングだけ401を返すサーバーもあるため、ストリーミングは知らせてつなぎ直しを続け、トークンが無効と分かったらセッションが止める
- 待っても直らない: そのほかの4xx、範囲指定に応えない応答、大きさの上限を超えた応答、読めない中身
- 回線で控えた: 質を上げると先読みの通信を、今の回線では送らないとOSが断った。時間をおいては読み直さない。回線が変わって行を描き直したときに、読むものを選び直す

## 自動の通信を止める

- 429や503が再開の時刻（`Retry-After`か`X-RateLimit-Reset`）を示したら、その単位の自動の通信を、時刻まで送らない。時刻を示していなければ止めない。いつまで止めればよいか分からないため
- 止めるのは、応答の頭を受け取った時点で行う。本文が上限を超えたり途中で切れたりして読めなくても、止める
- 止めるのは操作のほかの通信（自動の通信）だけで、操作は送る（上の「通信の目的」）
- 止める単位は、Mastodonが制限を数える単位に合わせる
  - ログインしたアカウントのAPIとストリーミングは、アカウントごと。Mastodonは、ログインしたアカウントごとに数えるため、同じサーバーの別のアカウントは止めない。ストリーミングも同じ門で止め、止めている間はつなぎ直さない
  - APIの外のURL（相手のサーバーの画像やファイル、fxtwitter、リンク先のページ）は、ホストごと。サーバーが時刻を示して止めたので、そのホストへの自動の通信を控える。絵文字、アイコン、添付ファイルのストアをまたいで止める。リダイレクトされていれば、応答したホストを止める
  - `/media_proxy`は、ここでは止めず、画像のストアごとに止める（[画像の読み込み](image-loading.md)）
- 止めている間に送ろうとした自動の通信は、待てば直る失敗にする。読み直す経路は、再開の時刻まで読み直さない

## 一時的な失敗

- その場での送り直し: GETと`Idempotency-Key`付きのリクエストは、502、504、再開の時刻のない503、通信の失敗で、1秒、2秒おいて2回まで送り直す。再開の時刻を示した応答は、止める単位のない`/media_proxy`でも、本文が途中で切れても、その場では送り直さない。時刻より前に送ることになるため。お気に入りなどは、サーバーに届いていたか分からないまま送り直すと意図しない結果になりうるため送り直さない。共有と保存のダウンロード（大きい）、範囲指定とリンクのタイトル（途中で読むのをやめる）、ストリーミング（つなぎ直しがある）は、その場では送り直さない
- あとからの読み直し: 各経路の間隔で読み直す。画像、Xの投稿、動画の最初のコマは、行を描いたときに、5秒から始めて倍にし、60秒で止める（チューニングで変えられる）。ストリーミングは、1秒から始めて倍にし、60秒で止める。応答が示した再開の時刻のほうが遅ければ、それまで待つ
- 待つ長さは、2割ずつ上下に散らす。サーバーが戻った直後に、同じ間隔で失敗した処理が同じ時刻に重ならないため。再開の時刻には散らす幅を足さない。サーバーが決めた時刻より早めることになるため

## 応答の大きさ

上限がないと、壊れたサーバーや悪意のあるサーバーが終わりのない本文を返したときに、メモリや端末の空きを使い切る。用途ごとに、ふつうの応答の大きさから余裕を見て決め（`ResponseLimit`）、超えたら読むのをやめて、待っても直らない失敗にする。長さを先に知らせる応答は、本文を読まずに断る。本文を届いた分から渡すときも、読む側が追いつかないうちに上限を超えて溜め込まない。

取り消されたら、途中まで受け取った本文を、読み終えたものとして扱わない。取り消された処理からは、新しい通信を送らない。呼び出し側が取り消しを失敗として飲み込み、次の読み込みへ進んでも、通信が出ないようにする。

| 用途 | 上限 | 決め方 |
|---|---|---|
| REST APIとログイン | 16MB | 大きいサーバーの`/api/v1/custom_emojis`がおよそ2.2MB（2026年10月のfedibird.com）で、その7倍ほど |
| 画像（絵文字、アイコン、添付ファイル、リンクのカード） | 32MB | Mastodonの添付の画像の上限が16MBで、ほかの実装のサーバーの画像を直接読むこともあるため、その倍 |
| Xの投稿 | 2MB | 4枚の画像の付いた投稿でも数十KB |
| 共有と保存のダウンロード | 1GB | Mastodonの動画の上限が99MBで、ほかの実装の長い動画も落とせるよう大きく取り、端末の空きを食いつぶさない範囲で止める |
| リンクのタイトル | 2MB | YouTubeの動画のページは全体で700KBほどで、og:titleは500KBを過ぎたあたりにある。超えたら失敗にせず、そこまでで探す |
| 動画の最初のコマ | 読む範囲の長さ | 動画の目次から決めた範囲だけを読む |

## 確かめ方

- どの経路の障害も、`scia-debug://status/<ステータス>?retry-after=<秒>&target=<経路>`でシミュレーターに起こせる（AGENTS.md）
