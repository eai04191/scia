# 保留中の通知

サーバーの通知のフィルタリング（`NotificationPolicy`）で保留した通知を見て、受け入れるか無視するかを選ぶ機能と、何を保留するかの設定について、作者が決めたこと。APIはMastodon 4.3から使える。4.2以前のサーバーでも通知は読めるため（[notification-display.md](notification-display.md)の「まとめて表示する」）、使えるかを確かめる仕組み（`OptionalFeature`の`notificationFilter`）に入れ、使えないと分かったら入口を出さない。

## 言葉

- 使う人に見える文言は、Mastodonのwebの日本語訳に揃える。画面の名前は「保留中の通知」、リクエストへの操作は「受け入れる」と「無視」、設定の画面は「通知のフィルタリング」、設定の選択肢は「受け入れ」「保留」「無視」
- サーバーのキーワードフィルター（[filters.md](filters.md)）と紛れないよう、使う人に見える文言で、保留した通知を「フィルターした通知」と書かない

## 入口

- 通知のタブのナビゲーションバーの右に、保留中の通知の画面を開くボタンを置く。保留している人がいるときは、ボタンに人数を添える。通知のタイムラインの行にしないのは、人数が変わるたびに行が出入りして、読んでいる行の位置が動かないようにするため
- ボタンの人数は、サーバーの`summary.pending_requests_count`をそのまま出す。サーバーが100で止めるので、100のときは「99+」のように丸めず「100+」と出す
- 人数を読み直すのは、通知のタイムラインを読み込んだとき、引っぱって読み直したとき、アプリに戻ったとき、受け入れや無視をしたあと、受け入れた通知の取り込みが終わったとき。保留した通知はストリーミングで届かないため、届いたときには読み直さない
- タブのバッジの未読の数には、保留中の通知を数えない
- サーバーに通知のフィルタリングのAPIがない（設定の読み込みが404などで返る）と分かったら、そのセッションの間は、このボタンとアカウントの画面の「通知のフィルタリング」を出さない。開いている設定の画面には、読めていた設定に代えて、このサーバーでは使えないことを出す

## 保留中の通知を送ってきた人のリスト

- `GET /api/v1/notifications/requests`で、サーバーが返すとおりの順に並べる。続きは応答の`Link`ヘッダーの`next`から読む
- 行は人のリスト（[account-list.md](account-list.md)）と同じく、アイコン、名前、ハンドルを並べ、その下に保留している通知の件数を出す。件数はサーバーが文字列で返す
- 行をタップすると、その人からの通知の画面を開く
- 行を長押しすると、「受け入れる」と「無視」を1つのまとまりで置き、その下にその人のユーザーのメニューを出す。この2つは並びの設定に載せず、隠したり動かしたりできない。フォローリクエストの通知の「承認」と「却下」と同じ扱い
- 行を左へスワイプすると「無視」、右へスワイプすると「受け入れる」を出す
- 受け入れると無視は、確かめずにすぐ送る。Mastodonのwebも1件ずつでは確かめないため
- 送れたら、使う人の操作で消える行なので、行を動かして消す。送れなかったら行を残し、チップで知らせる。404は、リクエストがもうない（ほかの端末で片づけたなど）ことなので、送れたときと同じく消す
- 何人分かを選んでまとめて受け入れる・無視する操作は、最初の版では作らない
- ナビゲーションバーの右に、通知のフィルタリングの設定を開くボタンを置く
- 保留している人がいなければ、「保留中の通知はありません」と出す

## その人からの通知

- `GET /api/v1/notifications?account_id=<ID>`で、その人からの通知を、通知のタブと同じ行の見た目で、まとめずに並べる。保留していない通知も並ぶ。v2はdocsに`account_id`があるが、Mastodonのサーバーは読まずにほかの人の通知も返すため、Mastodonのwebと同じくv1で読む。v1は`account_id`を渡すと、保留した通知も含めて返す
- まとめないので、通知を削除したときは、その通知だけを消す
- 見出しは「<名前>からの通知」にする
- ナビゲーションバーに「受け入れる」と「無視」のボタンを置く。Mastodonのwebと同じく、✓と✕のアイコンにする。文字のボタンにすると見出しがナビゲーションバーから押し出されて消えるため。済んだら保留中の通知の画面に戻り、その行を消す
- ストリーミング、既読位置、未読の数は持たない。新しく届いた通知は、引っぱって読み直すと出る

## 受け入れた通知の取り込み

- 受け入れると、サーバーは保留していた通知を通知のタイムラインへ戻す処理をあとで行う。終わったら、ストリーミングの`notifications_merged`で知らせる
- 知らせを受けたら、通知のタブのタイムラインを一番上から読み直して置き換える。取り込まれた通知は古い日時のものもあり、タイムラインの途中に入るため。読んでいた位置は保たない
- ストリーミングにつながっていないときは、受け入れたあとに`GET /api/v1/notifications/requests/merged`を間をあけて問い合わせ、終わっていたら同じく読み直す。つながっている間に受け入れて、知らせを受け取る前に切れたときは、つなぎ直したときに1回問い合わせる
- 知らせを受けたときにほかの読み込み（古い通知の読み込みなど）の途中なら、それが終わってから読み直す

## 通知のフィルタリングの設定

- アカウントの画面（[account-screen.md](account-screen.md)）と、保留中の通知の画面のナビゲーションバーの両方から開く
- 項目は、サーバーの`NotificationPolicy`の5つ。フォローしていないアカウント、フォローされていないアカウント、新しいアカウント、外部からの非公開の返信、モデレーションされたアカウントからの通知。それぞれ「受け入れ」「保留」「無視」から選ぶ
- 選んだらすぐ画面に反映し、`PATCH /api/v2/notifications/policy`で変えた項目だけを送る。続けて変えたときは、最後に選んだ値を残す。送れなかったら、サーバーに残っている値に戻してチップで知らせる
- 「無視」を選んだときは、Mastodonのwebと同じく確かめる。無視した通知はサーバーが作らず、あとから見られないため
- サーバーが知らない値を返した項目は、選べない形で「不明」と出し、送らない
