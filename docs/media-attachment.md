# メディアの添付

投稿へのメディアの添付で、作者が決めたこと。実装の細部と、公式に保証されていない挙動に頼っている箇所は、コードのコメントに書く。

## 選び方

- システムの写真ピッカーを、2段のシートで出す。低いときはキーボードと同じ高さで写真だけを並べ、最大のときはタブと検索と✓を出す。途中の高さでは止まらない
- 低いときに写真の上を上へスワイプすると、最大に広がる。下へスワイプするか✓を押すと閉じて、キーボードに戻る
- 選んだものは、その場で投稿欄に入る。開き直すと、前に選んだものが選ばれた状態で出る
- 低いときの高さは、チューニングで選ぶ

### ペーストで添付する

- 投稿欄の本文に、コピーした画像や動画をペーストして添付できる。ピッカーで選んだものと同じく、サムネイルの列の後ろに足し、すぐ送り始める
- クリップボードにメディアがあれば、文字がなくても編集メニューに「ペースト」を出す。UITextViewは、受け付ける形式に画像と動画を足しても、文字のないときは「ペースト」を出さないため
- クリップボードの項目ごとに振り分け、文字を持つ項目は本文に、文字を持たずに画像か動画を持つ項目は添付にする。文字とメディアを一緒にコピーしていれば、両方を取り込む
- 上限を超えた分は足さず、「上限を超えたため、画像2件を添付しませんでした」と数秒で消えるチップで知らせる。入る分だけ添付するのは、全部を断るより、入りきらない分を選び直すほうが手間が少ないため
- 注意書きの欄では、文字だけを受け付ける。注意書きにはメディアを付けられないため
- サーバーの上限をまだ読めていない間と、投稿を送っている間は、ピッカーと同じくメディアをペーストできない。「ペースト」は文字があるときだけ出す
- ペーストしたものは、ピッカーの選択に入れない。そのぶん、ピッカーで選べる枚数を減らす
- 写真アプリでコピーした写真は、HEICの写真もJPEGで届く。動画は元の形式で届く。複数を選んでコピーすると、1つずつ別の項目になる（シミュレーターで確かめた挙動で、ドキュメントには書かれていない）
- クリップボードの中身は後から変わるので、ペーストしたときにファイルをコピーし、あとから読み直さない。形式を処理できないサーバーへ送り直すときも、ピッカーのように同じ写真のJPEGを受け取り直さず、コピーしたファイルから、縮めるときと同じ品質でJPEGを作る

## 枚数とエラー

- 枚数の上限は、接続先のサーバーの値（`/api/v2/instance`の`max_media_attachments`）に合わせる。項目がなければ4にする
- 受け付けるかどうかはサーバーが決めるので、断られたらエラーとして伝える。伝え方は、エラーの伝え方の設計に合わせる

## 送る前に端末で縮める

通信量を減らし、アップロードを速くするために、送る前に端末で縮められるようにする。

### 設定

- 画像は「縮めない」「長辺4096px」「長辺2048px」、動画は「縮めない」「1080p」「720p」から選ぶ。標準は「長辺4096px」と「1080p」。iPhoneの標準の写真（4032×3024）と動画（1080p）はそのまま送られ、それより大きな写真と4Kの動画だけが縮む
- 形式を選ぶ設定は作らない
- モバイル通信のときだけ縮める設定は、今は作らない。使ってみて欲しくなったら足す

### 元のまま送るもの

- 選んだ大きさに収まるものと、「縮めない」を選んだときは、大きさを変えず、元のファイルのまま送る。ピッカーに形式を変えさせない。ピッカーに任せると、HEICの写真が、解像度はそのままで元より大きなJPEGになって届くため
- 大きさに収まるものを、形式を変えて小さくすることもしない。iPhoneのHEICは作り直してもほとんど小さくならず、画質だけが落ちる。元がJPEGの画像はHEICにすれば小さくなるが、大きさの設定の中で形式も変えると、設定の意味が分かりにくくなる
- 作り直すのは、選んだ大きさを超えるとき、サーバーがその形式を処理できないとき、サーバーの上限を超えるときだけにする

### サーバーの上限

- 上限は、`/api/v2/instance`の`configuration.media_attachments`にある値（`image_size_limit`、`image_matrix_limit`、`video_size_limit`、`video_matrix_limit`、`video_frame_rate_limit`）だけを使う。サーバーは容量や解像度を変えていることが多いので、MastodonやAPIで取れない既定値を前提にしない。返さない項目は推測で補わず、そのまま送ってサーバーの判断に任せる
- サーバーが保存するときに、どこまで縮めるか、どの形式に作り直すかも、APIで取れないので前提にしない
- 解像度は収まっていて容量だけが超えるとき、JPEGとHEICの画像は、解像度を保ったまま縮めるときと同じ品質で作り直し、それでも超えるときだけ解像度を段階的に下げる。容量は解像度より品質で大きく変わるため。PNGは品質を下げられないので、PNGのまま解像度を下げる。JPEGにすると、スクリーンショットの文字がにじみ、透過も消えるため
- 動画は、長さから上限に収まるビットレートを計算して書き出し、そのビットレートが解像度に対して低すぎるときは解像度を下げる。動画の長さは保ち、上限に収めるために後ろを切ることはしない
- 解像度を下げても見られる画質にならない長い動画は、縮めずに「動画が長すぎて、サーバーの上限に収められません」と失敗として知らせる。どれほど崩れても投稿できるより、使う人が動画を切って選び直せるほうがよいため。見られる画質の下限のビットレートは、チューニングで決める
- サーバーの上限に合わせて、選んだ大きさより小さく縮めたときや品質を下げたときは、使う人が選んでいない画質の変化なので知らせる。縮めたときに、種類に合わせて「画像をサーバーの上限に合わせて縮めました」「動画をサーバーの上限に合わせて縮めました」と数秒で消えるチップを出し、ビューアでその添付ファイルを開いたときに「上限に合わせて縮小 4032×3024→3840×2880」のように理由を出す。解像度を変えずに品質だけを下げたときは、「18.2 MB→15.1 MB」のように容量の変化を出す。ビューアのチップは画面の幅で切れるので、チップで伝えた「サーバーの」を省き、矢印の前後に空白を入れない。投稿欄のサムネイルには、ALTの札、閲覧注意の印、状態の表示がすでに重なっているので、印を足さない。失敗ではないので、「操作の状況」の「最近の失敗」には残さない

### 縮めるときの形式

- 画像は、サーバーの`supported_mime_types`に載っていればHEIC、なければJPEGで作り直す。元がPNG（スクリーンショットや透過画像）なら、PNGのまま縮める
- AVIFは使わない。iOSの書き出しでは、HEICとほぼ同じ大きさにしかならず、時間は数倍かかる。WebPは、iOSで書き出せない
- 動画はH.264で書き出す。HEVCのほうが小さくなるが、ブラウザによっては再生できず、サーバーがそのまま配信すると見られない人が出る。HDRの動画はSDRになるが、受け入れる。HDRの値をそのままSDRの値として書くと白っぽく浅い色になるので、AVAssetExportSessionのSDRのプリセットと同じAppleの標準の変換で、トーンマッピングと色域の変換をしてSDRにする
- 品質の値（画像の品質、動画の画質、上限に収めるときに残す余裕）は、使う人が変える値ではないので、設定ではなくチューニングに置く

### 形式を処理できないサーバー

- `supported_mime_types`に載っていても、処理できないサーバーがある。Mastodon 4.7.2と4.7.3は、HEIC、HEIF、AVIFを載せたまま、読み込みを止めている。HEICのまま送ると、`POST /api/v2/media`がその場で500を返す
- HEIC、HEIF、AVIFを送って500が返ったら、JPEGで1回だけ送り直す。そのサーバーのその版では、その形式を使わないと、起動をまたいで覚える。版で覚えるのは、サーバーが直ったらまた使うため
- 元のまま送ったファイルを送り直すときは、自分でJPEGを作らず、ピッカーに同じ写真のJPEGを要求する。ピッカーは元の形式と並べてJPEGも渡せ、今までピッカーに任せて送っていたものと同じ容量と画質になる。品質を自分で決めずに済み、いちばん高い品質で作ると容量が数倍になるため。ピッカーを開き直すと前に選んだ写真は読み直せないので、選んだときの受け取り口を持っておく
- 覚えたあとは、選んだ時点でピッカーにJPEGを要求し、送り直しを起こさない
- 縮めるために作り直したものを送り直すときは、縮めるときと同じ品質でJPEGを作る
- どちらの経路でも、JPEGはHEICより大きくなるので、送る前にサーバーの上限を確かめ直す。超えていたら、「サーバーの上限」の決まりどおりに上限に収めて知らせる
- 送り直したことは、見た目に分からないので添付した時点では知らせず、設定の「接続の状態」の「使っていない機能」に、止めた版と一緒に出す。この項目は起動し直しても消えないので、欄の説明に「サーバーの版が変わると、もう一度試します」を足す。どの添付で起きたかは、infoレベルで`SciaLog`に残す

### 位置情報

- 縮めるかどうかにかかわらず、送る前に画像と動画の位置情報を消す。サーバーが消すかはAPIで分からず、Mastodonのweb UIで投稿した画像にも位置情報は残らないため

### 投稿欄とビューアの表示

- 縮めたものは、縮めたあとの画像を出す。投稿される中身をそのまま確かめられるようにするため
- 動画の書き出しの間は、元の動画を出し、終わったら差し替える。添付から外したら書き出しを止める
- 書き出しとアップロードの進み具合は、1つの輪にまとめる（「添付ごとの状態」）。段階ごとに輪を出し直すと、一度満ちた輪がまた0から始まり、終わったと思ったところで戻って見えるため。サムネイルには段階の名前を出す場所がないので、段階は、VoiceOverの読み上げとビューアの状態の表示で示す

## 選んだメディアのプレビュー

選んだメディアは、投稿欄でサムネイルの列として見せ、タップするとタイムラインと同じビューアで開く。代替テキストはビューアの代替テキストの表示から入れ、並べ替えは列で行う。

### 見え方と操作

- 投稿欄の入力欄の上に、同じ大きさの正方形のサムネイルを横一列に並べる。上限が4枚より多いサーバーでも1段のまま全部見せ、並べ替えても枠の大きさは変えない
- 書いていないときは列を出さず、カプセルに1枚目のサムネイルを小さく出す（2枚以上なら3枚目までを重ねる）。決まりは[compose.md](compose.md)の「書いていないときの1行」にある
- サムネイルをタップすると、タイムラインと同じビューアがサムネイルから広がって開き、閉じるとサムネイルへ戻る。ピッカーのシートを出している間にタップしたときも、シートの上に開き、閉じるとシートと投稿欄はそのまま残る
- ビューアのメニューは「代替テキストを編集」「削除」にする。失敗したものには「再試行」も出す
- ビューアを開いている間も、投稿欄は書いている形のまま、キーボードの高さに留める
- 閉じたあと、キーボードは閉じる動きが終わってから戻す。それまでの間（シミュレーターで約0.5秒）、投稿欄とタブバーの間が空くのは受け入れる。空く時間が気になるかは実機で確かめる

### 代替テキストの入力

- ビューア下の代替テキストの帯は、空でも「代替テキストを追加」と出す。タップすると複数行の入力欄に変わり、キーボードのすぐ上に付く
- 入力中は、キーボードと入力欄に隠れない範囲に画像を縮めて収め、書きながら画像を見られるようにする
- 書いている間に画像の上をスワイプしても、ビューアは閉じない。まずキーボードを下げて書き終え、もう一度スワイプすれば閉じる
- 入力欄の中のドラッグ（スクロール、長押しからのカーソル移動）は、スワイプして閉じる操作とは別に、そのまま入力欄が受ける
- 上限（`description_limit`）に近づいたら、残りの文字数を出す
- アップロードが済む前にも書ける。書いた値は`DraftAttachment.description`に入れておき、アップロードと一緒に送る。済んだ後に書いたら、書き終えた時点で`PUT /api/v1/media/:id`を送る

### 並べ替え

- 列のコレクションビューのドラッグ&ドロップで並べ替え、ドロップの処理で並びを当て直す。iOS 15からは、iPhoneでも既定でドラッグできる（`dragInteractionEnabled`）
- VoiceOverとキーボードのために、セルに「先頭へ移動」「前へ移動」「後ろへ移動」「末尾へ移動」「削除」のカスタムアクションを付け、長押しのメニューにも同じ項目を置く
- ビューアの中では並べ替えない
- ピッカーは自分の順番で選択を送ってくるので、そのまま受け取ると、投稿欄で並べ替えた順が上書きされる。ピッカーからは、足したものと外したものだけを取り込み、並びはアプリ側の順番を保つ

### 添付ごとの状態

サムネイルの列に重ねて出し、ビューアでは上の中央（枚数の表示の近く）に同じ状態を出す。

| 状態 | 見せ方 |
|---|---|
| 書き出し中・送信中（`uploading`） | サムネイルを少し暗くし、円で進み具合を出す。端末での書き出しとアップロードを1つの円にまとめ、前半を書き出し、後半をアップロードに割り振る。割り振りは、かかる時間が動画の長さ、容量、電波で変わり予想できないので、チューニングで決める固定の割合にする。書き出さないものは、アップロードだけで円を満たす |
| 変換待ち（`processing`） | 円を回り続ける表示に替える |
| 済み（`uploaded`） | 何も重ねない。代替テキストがあればタイムラインと同じALTの札 |
| 代替テキストの送信中（`needsDescriptionUpdate`） | ALTの札の位置に小さく回る表示 |
| 失敗（`failed`） | 赤い感嘆符。タップで理由と「再試行」「削除」 |

投稿ボタンを押せるのは、全部が済んだときだけ。失敗の文言と出し方は、エラーの伝え方の設計に合わせる。

### 実装の決め事

- ビューアに「投稿欄から開いたか」の分岐を足さず、次の3つを外から渡す形に分ける。分岐を足していくと、閉じる操作や開閉の動きの条件が絡まるため
  - 描く中身: 種類・縦横比・代替テキスト・画像の出どころ（サーバーのURLか、手元のファイルとサムネイル）を持つ型をページに渡す。手元のファイルのURLで偽の`MediaAttachment`を作らない。IDがサーバーのものと混ざり、`MediaImageStore`が手元のファイルをキャッシュにコピーし、共有と保存が一時ファイルに効くため
  - 開閉の起点: 列のセルにも`MediaTileView`を置き、手元の画像を受け取れるようにする。閉じる動きは毎フレーム戻り先を探し直すので、投稿欄の位置が動いても追える
  - 操作: メニューの項目と、代替テキストの帯をタップしたときの動きを渡す
- 投稿欄から開くときは、Macで動かしていても`MediaWindow`の別ウィンドウにせず、その場で開く。別のシーンと下書きをつながずに済ませるため
- ビューアは、ピッカーのシートを出していればシートから、出していなければ投稿欄を置いた画面から出す
- 開く前に、入力欄のキーボードを自分で閉じる。開いている間は、`textViewDidEndEditing`で書いている状態を解かない。ビューアは表示されると最初の応答者になる（Escで閉じるため）ので、何もしないとキーボードが下がって投稿欄がカプセルに戻り、サムネイルの列が隠れて、閉じる画像の戻り先がなくなる
- 閉じる動きが終わってから、入力欄を最初の応答者に戻す。入力欄を最初の応答者のまま開くと、ビューアを閉じた時点でUIKitが入力欄にキーボードを戻し、シミュレーターでは閉じ始めの画像が約0.37秒止まった
- SciaCoreの`DraftAttachment`のほかに、アプリ側で`DraftAttachment.id`ごとに次を持つ
  - ピッカーの`assetIdentifier`との対応。ペーストしたものにはない
  - 端末で作ったサムネイルと、手元のファイルの場所。前に選んだ写真は、ピッカーに渡しても`itemProvider`が空で返る（PhotosUIのヘッダーに明記）ので、ピッカーから読み直せない
  - 種類と縦横比（サーバーの応答より前から、セルの印とビューアの枠に使う）
  - アップロードの進み具合
  - 失敗の理由。`DraftAttachment.State.failed`は理由を持たないため、投げられたエラーを持っておく。再試行が待ち直しか送り直しかも、これで分かる
  - 代替テキストの送信が失敗したこと（`needsDescriptionUpdate`のまま止まるため、送り直す操作と表示が要る）
